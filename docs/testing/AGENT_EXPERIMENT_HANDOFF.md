Improve real single-player Impossible performance through a repeated engineering loop:

1. **Identify and freeze.** Name the question, baseline, candidate, settings,
   source support, map/player count, spawn rule, cutoff and acceptance criteria.
2. **Play through MCP.** Use the actual installed extension in an owned Chrome
   profile, select official single-player Impossible, and confirm native spawn.
3. **Observe and record.** Preserve exact decisions, spend plans, native
   commands, runtime/source identities, screenshots, outcomes and missing data.
4. **Diagnose.** Locate the earliest meaningful failure, distinguish mechanism
   from correlation, and compare evidence with the verified native source.
5. **Improve one mechanism.** Implement a narrow change with a retained failing
   regression, independent math oracle, safety checks and a declared hypothesis.
6. **Retest the actual improved engine.** Reload its real extension build,
   verify active policy and run the assigned official Impossible matches again.
7. **Compare.** Use whole-match results under comparable conditions; include
   regressions, setup errors, timeouts, incomplete coverage and runtime cost.
8. **Deliver and repeat.** Push a scoped PR, verify its exact-head CI, merge
   authorized validated work, update clean main, then choose the next evidenced
   weakness. Rejected candidates remain documented; they need not be promoted.

The user authorized autonomous routine implementation decisions, pushing and merging. That does **not** authorize skipping failing checks, unsupported native commands, speculative production promotion, personal-profile access or unrelated changes. Ask only when materially new authority, an external dependency or a meaningful scope expansion is required. Preserve negative results instead of tuning the narrative.

### 5.6 Observe the match without assisting combat

Let the installed engine choose attacks, timing and allocation. MCP can inspect,
sample and take evidence; do not manually attack, adjust sliders, pause the
agent, change opponents or accelerate the scheduler during measured gameplay.
If an intervention is needed to debug, end/censor the assigned exposure and
record a separate diagnostic session with the intervention disclosed.

Record the start, first contact, first meaningful land loss, first prolonged
hold/dispatch stall, terminal/cutoff and any error. Use event-triggered evidence
for important transitions plus a bounded periodic sample. The recorder samples
approximately once per second and prints progress at the first/every 30th
sample; sequential reads and instrumentation can change the actual interval.
Do not convert those samples into exact death-event timing or independent trials.

Track native territory/bank/players/ticks, physical versus available contacts,
outgoing committed force, known directed incoming, exact decisions and budgets,
submitted/admitted/rejected command counts and reasons. Preserve screenshot and
native discrepancies; a black compositor image alone does not establish defeat.

When a tool call fails, preserve its stage/error and inspect current state before
acting again. A lost MCP connection is an observation gap, not proof that the
game froze or the policy lost. Record whether the actual engine kept running.

### 6.1 Record the actual calls without changing them

Inspect `runInternalFrame` in `content/content.js`. Capture immutable copies of the **existing** inputs and results at these stages:

1. Native observation used to build the situation: match ID, native/source state versions, tick and actual receipt time.
2. Exact `situation` supplied to `CORE.decide`, and that existing call's returned decision.
3. Decision after control-preference overrides; identify any changes explicitly.
4. Exact context passed to `CORE.planSpend`, and its full returned plan.
5. Post-hold/control changes, final ratio normalization, `maxSafeRatio` result, and actual `canFire` reasons.
6. Native command submission, result/error and receipt, using stable IDs linked to the decision/event.

**Do not call `decide` twice to obtain a recording.** The kernel contains observer state and timing-sensitive work; duplicate evaluation could alter behavior and cost. Do not infer refund/conquest from disappearance. Reuse verified native event facilities only when their contract supports the required meaning.

### 6.4 Bound recording and preserve behavior

Recording is opt-in, default-off and reversible. Use explicit event and byte caps, overflow/censor flags and incremental export. Choose/document limits, measure the largest supported state, and never silently drop difficult episodes. Do not export complete ownership rasters every tick.

Verify unchanged production decisions/spend with recording off **and on**, including across asynchronous receipt and state updates. Use the existing frozen 80-case fingerprint as a gate, not the only safety test. Test stale/mismatched states, immutable copies, timeout/error paths and no duplicate native calls.

### 6.5 Observe stable native owners and measure recording cost

`game.modern` is a newly generated facade on getter access. Wrapping a discarded

Current live observer defaults are **4,096 events and 4,194,304 serialized bytes

### 6.7 Diagnose the failure before choosing a change

Build a numerical timeline from the match start through the **first meaningful
divergence**, not only the final defeat. Align exact events where possible;
state samples between commands remain observations with timing uncertainty.

| Suspected mechanism | Evidence to inspect | Question that can falsify it |
| --- | --- | --- |
| Native/transport failure | Submissions, admissions, receipts, errors, freshness, target availability | Did the proposed command ever reach the sender, and was debit actually applied? |
| Opening overexposure | First-contact time, number/geometry of contacts, own bank versus known adjacent banks, committed fronts | Was a reserve-safe alternative feasible before contact, and what land/income would it sacrifice? |
| Excessive conservation | Final spend-block reason, reserve/defense wall, shrinking land, feasible reachable alternatives | Is there any command satisfying every current floor, or is the apparent opportunity unaffordable? |
| Poor target choice | Intended/admitted target, available versus physical neighbors, incoming direction, outgoing force | Did the target change in transit or was the weakness already in the selected action? |
| Unsupported combat forecast | Capture/settlement labels, reinforcement/refund events, intervening actions, horizon | Is the prediction scored on a complete supported episode or disturbed/censored data? |
| Spawn/geometry disadvantage | Predeclared spawn rule, reachable free land, bottlenecks, adjacent exposure | Is apparent policy improvement actually a different spawn/map distribution? |
| Endgame reachability | Remaining neutral cells/components, contacts/fronts and verified boat capability | Are opponents gone while official completion is still impossible through supported land commands? |

For each diagnosis write four separate statements: observed fact, verified
native mechanic, proposed explanation and unresolved alternative. A high bank,
a hold label, a long survival time or an opponent's large balance is not by
itself proof of an algorithmic bug. A failed command and a strategic hold are
different mechanisms; fix the one supported by the record.

Do not infer per-attack land/ROI from aggregate territory changes when other
attacks occur. The current gameplay recorder is not a complete native
capture/refund ledger. Extend supported per-attack episodes before making those
claims. Missing directed pressure or >32-actor coverage blocks conclusions
depending on those fields; it does not mean risk is absent.

### 6.8 Write a change contract before implementation

Record the baseline and candidate identities, one mechanism to change, inputs,
parameters and their provenance, scope, predicted benefit, possible regression,
measurement plan and explicit pass/fail/unsupported criteria. Select primary
outcome and safety gates before seeing treatment results.

A useful hypothesis is conditional and falsifiable, for example: a declared
contact cap may reduce early bank exposure while potentially sacrificing land
and income. Define how both effects will be measured. Do not write a conclusion
such as "this setting wins Impossible" as the hypothesis or silently tune
several thresholds, spawn rules and targeting logic in one unnamed candidate.

Implement on an isolated branch. Add the smallest retained failing regression
and an independent oracle/invariant, run the math protocol, inspect actual
orchestrator payloads and preserve source admission checks. Parameter changes
create a new candidate identity. If no safe feasible alternative exists, report
that negative finding rather than weakening a floor to manufacture a proposal.

| Candidate/observer/runtime cost | Median/P95/P99 and method | Median/P95/P99 and method | Comparable host/Chrome/settings; no inclusive-time double counting |

Fill this table with measured numbers and stated uncertainty, not fabricated
example values. A schema/status field is not evidence that its promised native
coverage or policy exposure actually occurred.

## 14. Failure handling and source-migration checklist

| Failure | Preserve and inspect | Correct response |
| --- | --- | --- |
| MCP tool unavailable or attached to the wrong browser | Tool metadata, intended browser, ownership/connection gap | Configure a supported owned connection; disclose CLI-only evidence if used |
| Extension absent, stale or from main instead of the candidate worktree | Installed ID/version, loaded path, runtime hash, fresh-tab state | Reload the exact tested extension and reacquire contexts before a new attempt |
| `contract-unmapped` / unknown source | Fetch/bootstrap metadata and available hashes, exact stage/error | Repair verified mapping; never add an unconditional whitelist or fabricate state |
| Observer cannot read the isolated agent | Extension-origin Runtime contexts and navigation timing | Reacquire the actual context; do not treat MAIN kernel status as original planner input |
| UI or spawn mismatch | Fresh snapshot, viewport, click sequence, native land freshness | Retain the failed attempt; correct the UI procedure in a distinct attempt |
| Command submitted but not admitted | Exact payload, native rejection/expiry, fresh state, reserve/target/front locks | Diagnose rejection; zero admitted commands cannot prove candidate execution |
| Incomplete >32 contact coverage or unknown bank/incoming | Physical IDs versus retained records and validity flags | Mark unsupported; extend a bounded observation path before relying on that risk view |
| Logs overflow, missing receipts or ambiguous joins | Bounds/drop/error counts, all unmatched records and intervals | Mark affected coverage incomplete; improve recording without changing actual decisions |
| Long holds during territory decline | Raw/final decision, full budgets, all floors, reachable alternatives | Test whether an alternative is actually feasible; do not remove safety floors from a loss alone |
| Source/runtime changes mid-cohort | Before/after identities and assigned attempt IDs | Close the incomplete freeze, preserve outcomes and start a new cohort |
| Last survivor with inaccessible neutral land | Native/UI completion evidence, components/fronts/boat capability | Record the milestone/capability gap; do not invent an official win |
| CI fails or reports an old head | Exact PR SHA, job conclusions and failure logs | Fix the relevant failure and wait for new-head checks; no bypass/false green status |

When a future source family is unknown, integration repair should establish:

1. Structural source recognition and a valid patch location; matching short
   obfuscated names alone is insufficient.
2. Verified player/bank/land/alive/match/clock/global-context and economy mappings,
   including validity and absence/error handling.
3. Physical adjacency, actionable/busy targets, front counts/caps, and actual
   directed incoming/outgoing force semantics.
4. Native quantization, tax/debit, meaningful force and reserve behavior through
   the **actual** human command path, with no duplicate admission or retargeting.
5. Opt-in observer/private-hook signature checks, bounded capture and exact
   restoration; unsupported spatial/event paths remain explicitly unsupported.
6. Original-call on/off invariance, immutable snapshots, timing/provenance and
   navigation-versus-executed-bootstrap identity.
7. Fresh native arithmetic/bootstrap/spatial checks appropriate to the changed
   path, existing historical fixtures, release isolation and all relevant CI.
8. A new real MCP/installed-extension UI/spawn/command observation on the
   supported official single-player Impossible configuration, followed by the
   prospective comparison required for any strength claim.

Until those gates pass, continue source/integration diagnosis and independent
math work while reporting live gameplay as unavailable. A documentation update,
passing original-routine VM comparison or successful Chrome launch alone does
not satisfy the missing installed-game step.
